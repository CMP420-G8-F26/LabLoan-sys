# Software Project Risks

For our Laboratory Equipment Loan and Return System, there are some risks that can affect the project during development. We identified the following risks and how we can manage them.

## R1 - Changing Requirements

**Risk Description:**
The requirements of the system might change while we are developing the project.

**Possible Cause:**
Students or laboratory staff might ask for new features or changes after we already started development.

**Probability:** Medium

**Impact:** Medium

**Mitigation/Response Strategy:**
We will discuss the main requirements before starting development and try to keep the project scope clear. If a new requirement comes up, we will discuss it as a team before adding it.

## R2 - Lack of Technical Skills

**Risk Description:**
Some team members might have problems using the programming tools or technologies needed for the system.

**Possible Cause:**
Some members may not have enough experience with web development, databases or other tools we use.

**Probability:** Medium

**Impact:** High

**Mitigation/Response Strategy:**
We will divide the tasks based on each team members skills. If someone has a problem with a technology, the other members can help and we can also research how to solve the problem.


## R3 - Project Schedule Delay

**Risk Description:**
The team might not finish all the required features on time.

**Possible Cause:**
Some features may take longer than expected, or team members may have other assignments and exams.

**Probability:** Medium

**Impact:** High

**Mitigation/Response Strategy:**
We will divide the project into smaller tasks and set deadlines for each part. We will also focus on the main features first such as equipment management, loan requests and returns.


## R4 - System Integration Problems

**Risk Description:**
Different parts of the system might not work correctly when they are combined.

**Possible Cause:**
Team members may develop different parts of the system using different approaches or structures.

**Probability:** Medium

**Impact:** High

**Mitigation/Response Strategy:**
We will agree on the main database and system structure before developing the different parts. We will also test the components together regularly instead of waiting until the end.


## R5 - Incorrect Equipment Information

**Risk Description:**
The equipment information stored in the system might be incorrect.

**Possible Cause:**
A laboratory staff member could enter incorrect equipment details, availability or condition.

**Probability:** Medium

**Impact:** High

**Mitigation/Response Strategy:**
We will use input validation and make important fields required. We will also limit equipment editing to authorized users.


## R6 - Unauthorized Access

**Risk Description:**
A user might access information or functions that they are not supposed to access.

**Possible Cause:**
Weak authentication or incorrect user permissions.

**Probability:** Low

**Impact:** High

**Mitigation/Response Strategy:**
We will use user authentication and different roles. Each role will only have access to the functions that they are allowed to use.


## R7 - Team Member Unavailability

**Risk Description:**
One of the team members may not be available to work on the project for some time.

**Possible Cause:**
Exams, other assignments, illness or scheduling problems.

**Probability:** Medium

**Impact:** Medium

**Mitigation/Response Strategy:**
We will divide the work between the team members and keep each other updated about the project. Important information should not only be known by one member.


## R8 - Users May Not Adopt the System

**Risk Description:**
Students or laboratory staff might not want to use the new system.

**Possible Cause:**
They may be used to the current manual way of managing equipment.

**Probability:** Medium

**Impact:** Medium

**Mitigation/Response Strategy:**
We will try to make the system simple and easy to use. We can also get feedback from potential users during development and make improvements based on their feedback.


## R9 - Loss of Project Data or Code

**Risk Description:**
Important project files or source code could be lost.

**Possible Cause:**
Computer problems, accidental deletion or incorrect changes to files.

**Probability:** Low

**Impact:** High

**Mitigation/Response Strategy:**
We will use GitHub for version control and make regular commits. This will allow us to recover previous versions if something goes wrong.


## R10 - Notification Problems

**Risk Description:**
The notification feature might not work correctly.

**Possible Cause:**
There could be problems in the implementation or configuration of the notification system.

**Probability:** Medium

**Impact:** Medium

**Mitigation/Response Strategy:**
We will test the notification feature during development. The system will also show the loan status and overdue information directly so users can still check their information.


# Risk Monitoring

The team will continue to monitor these risks during the development of the project. If a new risk appears, we will add it to the risk register. The probability and impact of a risk can also change as the project progresses.

We will pay more attention to high-impact risks such as security problems, integration problems and schedule delays because they could have a larger effect on the project.

# Conclusion

The main risks for our project are related to requirements, technical skills, time, system integration, data accuracy, security and team availability.

By identifying these risks early and monitoring them during development, we can try to reduce their effect on the project and improve the chances of completing the system on time.
